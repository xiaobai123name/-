# 04 检索系统

> 理解 RAG 的核心引擎——如何从大量文本块中找到最相关的内容。

---

## Q1：为什么检索是 RAG 系统中最关键的环节？

**A：** RAG 的质量取决于一个链条：

```
检索质量 → 上下文质量 → LLM 回答质量
```

如果检索返回的文本块与问题不相关，即使 LLM 再强大，也只能基于无关内容生成回答——这比没有检索还糟糕，因为 LLM 会「认真地基于错误上下文回答」。

所以检索系统的目标很简单：**在所有文本块中，找到与用户问题最相关的那几块**。

---

## Q2：什么是向量检索？它的优势和局限是什么？

**A：**

### 工作原理
1. 用户问题被转换为向量（query embedding）
2. 在向量数据库中找到与之距离最近的文本块向量
3. 返回对应的文本块

### 优势
- **语义理解**：「什么是注意力机制」能匹配到「attention mechanism 是一种...」
- **不依赖关键词**：用户的表述和文档的表述不需要完全一致

### 局限
- **对专有名词不敏感**：搜索「BERT」可能匹配到其他包含类似语义的内容
- **对精确匹配弱**：搜索某个公式编号、人名、缩写时效果差
- **受嵌入模型质量影响**：如果嵌入模型对某些领域理解不好，检索也会差

---

## Q3：什么是 BM25 关键词检索？它弥补了向量检索的什么不足？

**A：**

### BM25 是什么
BM25 是一种经典的**基于词频的文本相关性算法**，它不需要任何模型，直接根据关键词出现的频率和分布来计算相关性。

### 核心思想
- 一个词在某个文本块中出现次数越多 → 该块越相关
- 一个词在所有文本块中出现次数越少（越稀有） → 该词越重要
- 文本块越长，词频的权重适当降低（避免长文本占优）

### 弥补了什么
| 场景 | 向量检索 | BM25 |
|------|---------|------|
| 搜索「Transformer」 | 可能匹配到「变换器」「转换模型」 | 精确匹配「Transformer」这个词 |
| 搜索「公式 3.2」 | 语义上无法理解编号 | 精确匹配「公式 3.2」 |
| 搜索概念性问题 | 强项 | 弱项 |

**结论**：向量检索擅长语义，BM25 擅长精确关键词。两者互补。

## Q4：什么是混合检索（Hybrid Retrieval）？如何融合两路结果？

**A：**

### 混合检索的思路
同时执行向量检索和 BM25 检索，然后把两路结果融合成一个排序。

```
用户问题
  ├─ 向量检索 → 结果列表 A（按语义相似度排序）
  └─ BM25 检索 → 结果列表 B（按关键词相关性排序）
  │
  └─ RRF 融合 → 最终排序列表
```

### RRF（Reciprocal Rank Fusion）算法
这是融合多路检索结果的标准算法。核心思想：

**一个文本块如果在多路结果中都排名靠前，那它更可能是真正相关的。**

计算方式：
```
RRF_score(块) = Σ 1 / (k + rank_i)
```
- `rank_i` 是该块在第 i 路结果中的排名
- `k` 是常数（通常为 60），防止排名第 1 的权重过大
- 对每一路的倒数排名求和

**举例**：某个文本块在向量检索排第 2、BM25 排第 3：
```
RRF = 1/(60+2) + 1/(60+3) = 0.016 + 0.016 = 0.032
```

另一个块只在向量检索排第 1、BM25 中没出现：
```
RRF = 1/(60+1) + 0 = 0.016
```

前者的 RRF 分数更高，因为它在两路中都被认可。

## Q5：什么是重排序（Reranking）？为什么检索之后还需要重排？

**A：**

### 为什么需要重排
向量检索和 BM25 都有各自的偏差：
- 向量检索用的是通用嵌入模型，对特定领域可能不够准
- BM25 纯靠关键词，可能把只是碰巧包含关键词的无关块排上来
- RRF 融合后的排序仍然是粗排

**重排序**用一个专门的模型（Reranker），直接评估「问题-文本块」对的相关性分数，做更精准的排序。

### 重排模型 vs 嵌入模型
| 特性 | 嵌入模型 | 重排模型 |
|------|---------|---------|
| 输入 | 单独处理问题和文本块 | 同时处理问题-文本块对 |
| 速度 | 快（可以预计算） | 慢（需要对每个候选块单独打分） |
| 精度 | 较好 | 更好 |
| 用途 | 粗排（从万级块中选百级） | 精排（从十级块中选最终几个） |

所以流程是：先用向量+BM25 快速筛出 Top-K 候选（比如 10 个），再用重排模型精选 Top-N（比如 5 个）。

---

## Q6：本项目用的是什么重排模型？

**A：** 使用**硅基流动（SiliconFlow）API** 提供的 **BGE-Reranker** 模型。

BGE-Reranker 是智源研究院（BAAI）开发的开源重排模型，对中文有很好的支持。通过硅基流动的 API 调用，无需本地部署。

选择理由：
- 中文效果好
- API 调用简单（无需管理 GPU）
- 有免费额度

---

## Q7：什么是「自适应重排」？为什么不每次都重排？

**A：** 这是本项目的一个优化设计——**只在「不确定」的时候才调用重排模型**。

### 判断依据
看 RRF 融合后的第 1 名和第 2 名的分数差距：
- 如果差距大（> `CONFIDENCE_THRESHOLD`，默认 0.15）：说明第 1 名远超其他候选，直接使用，不需要重排
- 如果差距小（≤ 0.15）：说明多个候选难分伯仲，需要重排来精细排序

### 为什么这样设计
- 重排模型是外部 API 调用，有成本和延迟
- 很多时候检索结果已经足够明确，重排是浪费
- 只在真正需要时才重排，兼顾了效果和效率

## Q8：检索结果中子块和父块是如何配合的？

**A：** 这是**父文档检索**（Parent Document Retrieval）模式：

```
步骤 1：用子块做检索（精准匹配）
  用户问题 → 匹配到子块 A1, B3, C2

步骤 2：找到对应的父块（完整上下文）
  子块 A1 → 父块 A
  子块 B3 → 父块 B
  子块 C2 → 父块 C

步骤 3：返回父块内容给 LLM
  LLM 看到的是父块 A、B、C 的完整内容
```

**为什么不直接用父块检索？**
- 父块太大（2000 字符），里面可能只有一小段和问题相关，其余是噪声
- 大块嵌入的向量会被无关内容「稀释」，降低匹配精度

**为什么不直接用子块给 LLM？**
- 子块太小（500 字符），可能截断了完整的论述
- LLM 需要更多上下文才能生成连贯的回答

## Q9：检索时如何实现「范围过滤」？

**A：** 用户可以选择在哪些文档范围内搜索：

- **全部文档**：搜索用户的所有已处理文档
- **指定文档**：只搜索用户选定的几份文档

实现方式是在向量检索时传入**元数据过滤条件**。每个向量在存入 ChromaDB 时都附带了 `user_id` 和 `document_id` 元数据，检索时可以按这些字段过滤。

BM25 检索也做相应的文档范围过滤。

---

## Q10：整个检索流程的完整链路是什么？

**A：** 整合以上所有环节：

```
用户输入问题
    │
    ├─ 问题向量化（query embedding, task_type=retrieval_query）
    │
    ├─ 向量检索：在 ChromaDB 中搜索 Top-K 相似子块
    │      └─ 按 user_id / document_id 过滤
    │
    ├─ BM25 检索：在同范围的子块文本上做关键词匹配
    │
    ├─ RRF 融合：合并两路结果，按融合分数排序
    │
    ├─ 自适应重排（可选）
    │      └─ Top-1 和 Top-2 分数差 ≤ 阈值时启动
    │      └─ 用 BGE-Reranker 重新排序
    │
    ├─ 取 Top-N 子块
    │
    └─ 子块 → 父块映射，返回父块内容
           └─ 最终给 LLM 的上下文
```

---

## Q11：如果检索到的内容不相关怎么办？

**A：** 系统有几道防线：

1. **混合检索**：两路互补，减少单路漏检
2. **重排模型**：进一步过滤假阳性
3. **Prompt 设计**：RAG 的 Prompt 中明确要求 LLM「如果提供的上下文无法回答问题，请明确说明」
4. **引用标注**：每个回答都附带引用来源，用户可以自行验证

但如果用户上传的资料本身就不包含相关内容，系统确实无法回答——这正是 RAG 的特点：**只基于已有资料回答**。
