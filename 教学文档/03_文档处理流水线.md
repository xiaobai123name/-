# 03 文档处理流水线

> 理解文档从上传到可被检索的完整处理过程。

---

## Q1：用户上传一份 PDF 后，系统会经历哪些步骤？

**A：** 完整的处理流水线包含四个阶段：

```
上传文件 → 解析（Parser） → 分块（Chunker） → 向量化（Embedder）
```

具体来说：
1. **保存文件**：将原始文件存到 `data/uploads/` 目录
2. **创建记录**：在数据库 Document 表中创建一条记录，状态标记为「处理中」
3. **解析**：根据文件类型选择不同的解析器，提取纯文本和元数据
4. **分块**：将长文本切成父块和子块
5. **向量化**：将每个块转换为向量，存入 ChromaDB
6. **更新状态**：将 Document 记录状态更新为「已完成」，记录块数

任何一步失败，状态会更新为「失败」并记录错误信息。

---

## Q2：文档解析（Parser）支持哪些格式？不同格式的处理有什么区别？

**A：**

| 格式 | 解析方式 | 特点 |
|------|---------|------|
| **PDF** | PyPDF / pdfplumber / LlamaParse | 最复杂，可能有扫描页、多栏排版 |
| **Word (.docx)** | python-docx | 结构化好，段落标题清晰 |
| **Markdown (.md)** | markdown 库 | 最简单，纯文本带标记 |

**PDF 的特殊处理**：
- 默认用 PyPDF 提取文本（速度快、免费）
- 如果配置了 LlamaParse API Key，则用 LlamaParse（效果更好，尤其是复杂排版）
- 解析结果包括：纯文本内容、页码信息、文件哈希

**解析输出**统一为 `ParsedDocument` 结构，包含：文本内容、各页文本、元数据、文件哈希。无论什么格式，后续的分块器拿到的都是统一格式。

---

## Q3：为什么需要分块（Chunking）？直接把整篇文档送给 LLM 不行吗？

**A：** 不行，原因有三：

### 1. LLM 上下文窗口有限
即使现代 LLM 支持很长的上下文（如 100K token），把整篇教材塞进去也会：
- 浪费 token（按量计费）
- 导致 LLM「注意力分散」，回答质量下降

### 2. 检索需要粒度
如果不分块，向量搜索只能在「整篇文档」级别匹配。但用户的问题通常只和文档中某几段相关，需要更细粒度的检索。

### 3. 引用定位
分块后可以精确告诉用户「答案来自第 X 页第 Y 段」，整篇文档无法提供这种精确引用。

---

## Q4：分块策略是什么？为什么采用「父子块」设计？

**A：** 采用的是**递归字符分割 + 父子块两级结构**。

### 分块参数
| 参数 | 默认值 | 含义 |
|------|-------|------|
| `PARENT_CHUNK_SIZE` | 2000 字符 | 父块大小 |
| `CHUNK_SIZE` | 500 字符 | 子块大小 |
| `CHUNK_OVERLAP` | 50 字符 | 子块之间的重叠 |

### 分块过程
```
原始文本
  │
  ├─ 按段落/标题先切成父块（~2000字符）
  │
  └─ 每个父块内部再细切成子块（~500字符，相邻重叠50字符）
```

### 为什么要两级？

这是 **"小块检索、大块生成"** 策略：

| 用途 | 块类型 | 大小 | 原因 |
|------|-------|------|------|
| 检索匹配 | 子块 | ~500 字符 | 小块语义更聚焦，检索更精准 |
| 送给 LLM | 父块 | ~2000 字符 | 大块上下文更完整，回答更连贯 |

如果只用小块，LLM 看到的上下文可能断章取义；如果只用大块，检索时一大段中混入不相关内容会拉低匹配度。两级结构是两者的最优折中。

---

## Q5：子块之间为什么要重叠（Overlap）？

**A：** 重叠是为了解决**边界信息丢失**问题。

假设一段关键内容恰好在两个块的分界处：
```
块 A: ...Transformer 模型采用了自注意力机制，
块 B: 使得模型能够同时关注输入序列的所有位置...
```

如果没有重叠，搜索「自注意力机制的作用」可能两个块都匹配度不高。有了 50 字符的重叠，块 B 的开头会包含块 A 末尾的内容，确保完整语义被至少一个块捕获。

---

## Q6：递归字符分割是什么意思？

**A：** 分割时按**优先级递降的分隔符**列表进行：

```
优先级从高到低：
  "\n\n"（段落分隔）
  → "\n"（换行）
  → "。"（句号）
  → "；"（分号）
  → "，"（逗号）
  → " "（空格）
  → ""（逐字符）
```

工作过程：
1. 先尝试按段落（`\n\n`）分割
2. 如果分出的块仍然太大，换下一级分隔符继续切
3. 直到块大小满足要求

好处是**尽量在语义自然断点处切割**，避免在句子中间切开。

---

## Q7：向量化（Embedding）是做什么的？

**A：** 向量化是把文本转换成一个高维数字向量（比如 768 维），使得**语义相似的文本在向量空间中距离很近**。

```
"什么是注意力机制" → [0.12, -0.34, 0.56, ..., 0.78]  (768个数字)
"attention mechanism 的含义" → [0.11, -0.33, 0.57, ..., 0.77]  (很相近)
"今天天气不错" → [-0.45, 0.23, -0.12, ..., 0.01]  (距离很远)
```

这样做的目的是让计算机能够理解「语义相似度」——用户的问题和文档块之间的匹配不再依赖关键词完全一致，而是基于含义。

---

## Q8：向量化支持哪些提供商？为什么要区分 retrieval_document 和 retrieval_query？

**A：**

### 支持的嵌入提供商
| 提供商 | 模型 | 特点 |
|--------|------|------|
| **Google** | gemini-embedding-001 | 官方模型，质量高 |
| **Antigravity** | 可配置 | OpenAI 兼容接口的替代方案 |

### 任务类型区分
Google 的嵌入 API 支持指定**任务类型**：
- `retrieval_document`：用于**存储时**嵌入文档块
- `retrieval_query`：用于**查询时**嵌入用户问题

两者生成的向量在空间中的优化方向不同，同一个文本用不同任务类型得到的向量会有差异。这种区分能**提升检索精度**——文档向量和查询向量在各自空间中更好地对齐。

---

## Q9：向量化后的数据存在哪里？如何组织？

**A：** 向量存入 ChromaDB，组织方式如下：

- 每个向量附带**元数据**：用户 ID、文档 ID、块类型（parent/child）、父块 ID
- 检索时可以按元数据过滤（比如只搜某个用户的、只搜某个文档的）
- ChromaDB 使用 HNSW 索引实现快速近似最近邻搜索

同时，块的文本内容和元数据也存入 SQLite 的 Chunk 表，这样即使不走向量搜索，也能通过数据库查询获取块内容。

---

## Q10：如果文档处理失败了怎么办？

**A：** 系统有**状态追踪和错误处理**机制：

1. **状态流转**：`pending → processing → completed / failed`
2. **失败记录**：Document 表有 `process_status` 字段记录状态
3. **用户感知**：前端文档管理页面会显示每个文档的处理状态
4. **可重试**：用户可以删除失败的文档重新上传

在解析、分块、向量化的每个阶段如果出现异常，都会被捕获并将文档状态标记为失败。

---

## Q11：这个流水线的设计有什么可扩展性考虑？

**A：** 几个可扩展的设计点：

| 扩展方向 | 当前设计如何支持 |
|---------|---------------|
| **新增文件格式** | Parser 模块是按格式分离的，新增格式只需加一个解析函数 |
| **切换嵌入模型** | Embedder 通过 `EMBEDDING_PROVIDER` 配置切换，新增只需实现统一接口 |
| **调整分块策略** | 分块参数全部可配置，父子块大小可通过 `.env` 调整 |
| **更换向量数据库** | VectorStore 是一个封装层，底层从 ChromaDB 换成 Pinecone 等只需改实现 |
