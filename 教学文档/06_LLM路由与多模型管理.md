# 06 LLM 路由与多模型管理

> 理解系统如何支持多个 LLM 供应商，并为不同功能模块分配不同模型。

---

## Q1：为什么需要支持多个 LLM 供应商？

**A：** 三个实际原因：

### 1. 成本优化
不同任务对模型质量的要求不同：
- 问答需要高质量回答 → 用贵但好的模型
- 知识图谱需要大量调用 → 用便宜的模型
- 一个供应商可能只擅长某类任务

### 2. 可用性保障
单一供应商可能遇到：
- API 配额用完
- 服务暂时不可用
- 特定地区访问受限

多供应商意味着可以在一个不可用时切换到另一个。

### 3. 灵活性
用户可以根据自己拥有的 API Key 选择供应商，不强制绑定某一家。

---

## Q2：项目支持哪些 LLM 供应商？它们有什么区别？

**A：**

| 供应商 | 接口协议 | 典型模型 | 特点 |
|--------|---------|---------|------|
| **Google Gemini** | Google AI SDK | gemini-2.5-flash | 官方 SDK，支持多模态，中文好 |
| **硅基流动** | OpenAI 兼容 | 多种开源模型 | 国内访问友好，价格低 |
| **Antigravity** | OpenAI 兼容 | 可配置 | 代理网关，统一 OpenAI 接口 |

### OpenAI 兼容接口是什么？
很多 LLM 供应商采用了与 OpenAI 相同的 API 格式（`/v1/chat/completions`），只需要换一个 `api_base` 地址和 `api_key` 就能切换。这大大简化了多供应商接入的工作。

---

## Q3：ModelRouter 的核心设计思想是什么？

**A：** ModelRouter 是整个多模型系统的**中枢调度器**，核心思想是**按用户 + 按模块路由**。

```
前端请求: "我要进行 RAG 问答"
    │
    ▼
ModelRouter.get_chat_model(user_id=1, module="rag")
    │
    ├─ 查询数据库: 用户 1 的 RAG 模块配置了什么模型？
    │   └─ 找到: provider=google, model=gemini-2.5-flash
    │
    ├─ 创建对应的 ChatModel 实例
    │
    └─ 返回可直接调用的模型对象
```

调用方只需要告诉 Router「我是谁、我在做什么」，Router 负责返回正确的模型——调用方不需要关心底层是 Google 还是硅基流动。

---

## Q4：系统定义了哪些功能模块？为什么要按模块配置模型？

**A：** 四个功能模块：

| 模块标识 | 功能 | 模型需求特点 |
|---------|------|------------|
| `rag` | RAG 问答 | 需要高质量生成、理解引用格式 |
| `socratic` | 苏格拉底对话 | 需要引导式提问能力 |
| `quiz` | 测验生成 | 需要生成结构化的题目和选项 |
| `kg` | 知识图谱 | 需要从文本抽取实体/关系，调用量大 |

**按模块配置的价值**：
- KG 模块调用量大 → 用便宜模型控制成本
- RAG 模块对质量要求高 → 用最好的模型
- Quiz 模块需要结构化输出 → 用对 JSON 生成更可靠的模型

用户可以在设置页面为每个模块独立选择供应商、模型和参数。

---

## Q5：如果用户没有配置模型偏好，系统怎么处理？

**A：** 采用**三级回退策略**：

```
1. 首先查询: 用户在数据库中是否有该模块的偏好？
   └─ 有 → 使用用户配置

2. 没有，则使用: .env 中配置的全局默认模型
   └─ LLM_MODEL = gemini-2.5-flash

3. 如果 .env 也没配置: 使用代码中的硬编码默认值
```

这样既保证了灵活性（用户可自定义），又保证了开箱即用（有合理的默认值）。

## Q6：NormalizedChatModel 解决了什么问题？

**A：** 解决的是**不同供应商返回格式不统一**的问题。

### 问题
- Google SDK 返回的结果格式和 OpenAI 兼容接口不同
- 有的返回字符串，有的返回对象
- 流式和非流式的接口也有差异

### 解决方案
NormalizedChatModel 是一个**包装层**，无论底层是什么供应商，统一提供：
- `invoke(prompt)` → 返回字符串
- `ainvoke(prompt)` → 异步返回字符串
- `stream(prompt)` → 返回字符串流

调用方拿到的永远是一个行为一致的对象，不需要关心底层差异。这是**适配器模式**的典型应用。

---

## Q7：SiliconFlowChatModel 的设计目的是什么？

**A：** 硅基流动和 Antigravity 都使用 OpenAI 兼容接口，但 LangChain 的 ChatOpenAI 类在某些场景下不完全兼容（比如重排器 API）。

SiliconFlowChatModel 是一个**自定义的轻量级客户端**，直接用 `httpx` 调用 OpenAI 兼容的 `/v1/chat/completions` 接口，好处是：
- 完全控制请求和响应的处理逻辑
- 支持流式输出
- 可以处理供应商特有的响应格式差异
- 不依赖 LangChain 的 OpenAI 集成

---

## Q8：模型配置存储在哪里？

**A：** 两层存储：

| 层次 | 位置 | 内容 |
|------|------|------|
| **全局默认** | `.env` 文件 | `LLM_MODEL`、API Key 等 |
| **用户偏好** | SQLite `UserModelPreference` 表 | 每个用户每个模块的配置 |

API Key 只存在 `.env` 中（安全考虑），不存入数据库。用户偏好只存储模型名称、供应商、温度等非敏感信息。

---

## Q9：温度（Temperature）参数是什么？为什么不同模块需要不同的温度？

**A：**

### 温度是什么
温度控制 LLM 输出的**随机性**：
- `temperature = 0`：每次输出几乎相同，最确定性
- `temperature = 1`：输出更随机、更有创意
- `temperature > 1`：非常随机，可能不连贯

### 不同模块的温度需求

| 模块 | 推荐温度 | 原因 |
|------|---------|------|
| RAG 问答 | 0.3-0.5 | 需要准确性，不要创造性 |
| 知识图谱 | 0.1-0.3 | 抽取实体需要严格遵循格式 |
| 测验生成 | 0.5-0.7 | 需要一定多样性，出不同的题 |
| 苏格拉底 | 0.5-0.7 | 需要灵活的提问方式 |

## Q10：如果某个 API 调用失败了怎么办？

**A：** 系统使用了 `tenacity` 库进行**重试机制**：

- 遇到临时性错误（网络超时、API 限流）时自动重试
- 重试之间有指数退避（等待时间逐次增加）
- 最多重试 N 次后放弃，向上层报错

此外，知识图谱模块还有专门的速率限制（Rate Limiting）：
- 控制每分钟 LLM 调用次数（RPM）
- 控制每分钟嵌入调用次数
- 使用信号量控制并发数

这些都是为了避免触发 API 供应商的限流机制。

---

## Q11：这个多模型架构的可扩展性如何？

**A：** 新增一个 LLM 供应商只需要：

1. 在 ModelRouter 中增加一个供应商分支
2. 如果是 OpenAI 兼容接口，几乎零开发量（改配置即可）
3. 如果是自定义接口，实现 `invoke/stream` 两个方法即可

不需要修改任何调用方的代码——因为调用方只和 NormalizedChatModel 交互。
