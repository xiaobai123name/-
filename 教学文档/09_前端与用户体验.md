# 09 前端与用户体验

> 理解 Streamlit 前端的组织方式、页面结构和用户交互设计。

---

## Q1：为什么选择 Streamlit 作为前端框架？

**A：** Streamlit 在本项目场景下有三个关键优势：

| 优势 | 说明 |
|------|------|
| **纯 Python** | 不需要写 HTML/CSS/JavaScript，对 AI/ML 开发者友好 |
| **快速原型** | 几十行代码就能搭出交互式 Web 应用 |
| **内置组件** | 聊天界面、文件上传、图表、进度条等开箱即用 |

**权衡**：Streamlit 的 UI 定制能力不如 React/Vue，但对于学术毕设项目，开发效率远比 UI 灵活性重要。

---

## Q2：Streamlit 多页应用是如何组织的？

**A：** Streamlit 有一个内置的多页应用机制：

```
app/
├── 主页.py          ← 主入口（streamlit run app/主页.py）
└── pages/
    ├── 1_智能问答.py  ← 自动成为侧边栏导航项
    ├── 2_文档管理.py
    ├── 3_测验练习.py
    ├── 4_知识图谱.py
    └── 5_设置.py
```

**规则**：
- `pages/` 目录下的 `.py` 文件自动注册为页面
- 文件名前的数字（`1_`、`2_`）控制排列顺序
- 下划线后的中文名就是侧边栏中显示的页面名称
- 用户点击侧边栏即可切换页面

---

## Q3：每个页面的通用结构是什么？

**A：** 所有页面遵循统一的结构模式：

```
1. 初始化（init_session）
   ├─ 检查认证状态（未登录则跳回主页）
   ├─ 恢复 Cookie 登录
   └─ 初始化页面所需的后端组件（存入 session_state）

2. 侧边栏（sidebar）
   ├─ "返回主页" 按钮
   ├─ 页面相关的操作选项
   └─ 统计信息或快捷功能

3. 主内容区
   └─ 页面的核心功能界面
```

这种统一结构带来一致的用户体验——无论在哪个页面，都能快速返回主页，都能在侧边栏找到操作入口。

## Q4：session_state 在 Streamlit 中扮演什么角色？

**A：** `st.session_state` 是 Streamlit 中**最重要的状态管理机制**。

### 为什么需要
Streamlit 的工作方式是**每次用户交互，整个脚本从头重新执行**。这意味着：
- 普通变量每次执行都会重置
- 数据库连接、模型实例等需要在多次执行之间保持

### 存储了什么
| 内容 | 举例 |
|------|------|
| **用户信息** | user（当前登录用户） |
| **后端实例** | db_manager、vector_store、rag_chain |
| **页面状态** | 聊天历史、当前测验、选中的文档 |
| **UI 状态** | 展开/折叠、选中的选项卡 |

### 设计原则
- 首次运行时初始化（`if "xxx" not in st.session_state`）
- 后续运行时直接复用
- 需要重置时显式清除

## Q5：主页（仪表盘）的设计逻辑是什么？

**A：** 主页在用户登录后展示仪表盘，设计上起到**信息汇总 + 行动引导**的双重作用：

### 信息汇总
四个核心指标卡片：
| 指标 | 含义 | 数据来源 |
|------|------|---------|
| 文档总数 | 已上传处理的文档数 | Document 表 |
| 掌握知识点 | 掌握率 ≥ 60% 的知识点数 | KnowledgeState 表 |
| 答题总数 | 历史总答题次数 | QuizAttempt 表 |
| 错题数 | 答错的题目总数 | QuizAttempt 表（is_correct=False） |

### 行动引导（智能建议）
根据用户数据动态生成建议：
| 用户状态 | 建议 |
|---------|------|
| 没有文档 | 「先上传学习资料吧」→ 跳转文档管理 |
| 有文档但没答题 | 「试试测验练习」→ 跳转测验 |
| 有错题 | 「有 N 道错题，建议复习」→ 跳转错题本 |
| 有薄弱知识点 | 「这些知识点需要加强」→ 跳转专项练习 |

### 最近足迹
时间线形式展示最近的活动（上传、对话、错题），帮助用户回顾学习轨迹。

## Q7：文档管理页面的交互设计有什么亮点？

**A：**

### 上传流程（带进度反馈）
```
拖拽/选择文件
    │
    ├─ 显示文件信息（名称、大小、格式）
    │
    └─ 点击处理 → 进度条依次展示：
         保存文件 ████████░░ 40%
         解析文档 ██████████ 60%
         文本分块 ████████████ 80%
         向量化   ██████████████ 100%
         ✅ 处理完成！
```

### 文档列表
每个文档显示为卡片：
- 文件名、类型图标、上传时间
- 处理状态（已完成 / 处理中 / 失败）
- 块数统计
- 删除按钮

### 设计要点
- 进度反馈让用户知道系统在做什么（不是卡死了）
- 卡片式布局比列表更直观
- 删除有确认防误操作

## Q8：测验页面的交互设计有哪些考虑？

**A：**

### 出题流程
```
选择出题方式
├─ 综合复习：选择文档 → 设置题目数 → 生成
└─ 专项突破：选择薄弱知识点 → 生成

生成过程中显示加载动画
```

### 答题流程
```
显示题目和选项
    │
    ├─ 用户选择答案
    │
    └─ 提交 → 判断对错
         ├─ 正确：✅ 恭喜！显示解析
         └─ 错误：❌ 显示正确答案 + 解析 + 追问题
```

### 侧边栏设计
- 学习统计（答题数、正确率 → 直观的数字）
- 薄弱知识点快捷入口
- 错题本 Top 5（方便快速复习）

## Q9：知识图谱页面的交互设计是怎样的？

**A：**

### 操作流程
```
侧边栏：
  选择文档（单个/全部）
  └─ 全部文档时可选策略（逐文档/全局）
  └─ 点击"构建图谱"
  └─ 等待构建（可能需要几分钟）

主区域：
  交互式图谱
  └─ 可拖拽、缩放
  └─ 点击节点查看详情
  └─ 不同实体类型用不同颜色区分
```

### 设计考量
- 图谱构建耗时较长 → 需要明确的加载状态
- 图可能很大 → 提供聚焦模式（只看选中节点的周围）
- 实体搜索 → 在大图中快速定位某个概念

## Q10：设置页面的设计考虑是什么？

**A：** 设置页面分为五个选项卡（Tab），层次清晰：

| Tab | 内容 | 目标用户 |
|-----|------|---------|
| **API 配置** | 各供应商的 API Key 管理 | 首次使用时配置 |
| **用户设置** | 修改用户名、密码 | 日常管理 |
| **RAG 参数** | 分块大小、检索数量等 | 进阶用户调优 |
| **数据管理** | 清空文档、查看统计 | 数据维护 |
| **模型选择** | 各模块的模型配置 | 按需调整 |

### 设计要点
- 常用功能放前面（API → 用户 → RAG → 数据 → 模型）
- 危险操作（清空数据）有二次确认
- RAG 参数只展示，修改需要改 `.env`（避免用户误操作影响系统稳定性）

## Q11：页面之间是如何跳转的？有什么导航策略？

**A：**

### 跳转方式
使用 `st.switch_page()` 函数进行编程式导航。

### 导航策略
```
主页 → 各功能页面（通过快捷入口/智能建议）
各功能页面 → 主页（通过侧边栏"返回主页"）
无文档时 → 自动引导到文档管理页面
```

### 关键跳转场景
| 触发条件 | 跳转目标 | 原因 |
|---------|---------|------|
| 未登录 | 主页（登录页） | 需要认证 |
| 无文档时进入问答/测验/图谱 | 文档管理 | 这些功能依赖文档 |
| 主页建议「上传资料」 | 文档管理 | 引导操作 |
| 主页建议「复习错题」 | 测验练习 | 引导操作 |

## Q12：前端如何实现自定义样式？

**A：** 主页通过 `st.markdown()` 注入自定义 CSS，实现 Notion 风格的视觉效果：

- 指标卡片样式（圆角、阴影、色彩）
- 时间线样式（最近足迹）
- 按钮样式（快捷入口）
- 整体色调和间距

其他页面保持 Streamlit 默认样式，保证一致性和开发效率。
