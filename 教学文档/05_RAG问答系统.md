# 05 RAG 问答系统

> 理解检索到内容后，如何组装 Prompt、调用 LLM、生成带引用的回答。

---

## Q1：RAG 的完整流程是什么？

**A：** RAG（Retrieval-Augmented Generation）的流程可以拆成三步：

```
R（Retrieval）检索
  → 从向量库中找到与问题相关的文本块（上一节已讲）

A（Augmented）增强
  → 将检索到的文本块作为上下文，与问题一起组装成 Prompt

G（Generation）生成
  → 将 Prompt 送给 LLM，生成回答
```

本项目的 RAG 模块（`backend/rag/`）主要负责后两步：Prompt 组装和 LLM 调用。

---

## Q2：Prompt 是如何设计的？

**A：** Prompt 的设计是 RAG 质量的关键。本项目的 Prompt 结构大致如下：

```
系统指令（System Prompt）
  ├─ 你是一个学习助手
  ├─ 基于以下参考资料回答问题
  ├─ 如果资料中没有相关内容，明确说明
  └─ 在回答中标注引用来源

参考资料（Context）
  ├─ [来源1: 文档名, 页码] 文本块内容...
  ├─ [来源2: 文档名, 页码] 文本块内容...
  └─ ...

对话历史（History）
  ├─ 用户之前的问题
  └─ 助手之前的回答

当前问题
  └─ 用户的提问
```

### 关键设计原则

1. **明确限制知识来源**：要求 LLM 只基于提供的参考资料回答，不要使用自身训练知识
2. **要求引用标注**：每个论述都要标注来自哪份资料
3. **诚实承认不知道**：如果资料中没有答案，要明确告知用户
4. **保持对话连贯**：加入对话历史，使多轮对话自然流畅

---

## Q3：对话历史（Memory）是如何管理的？

**A：** 对话历史管理要解决一个核心矛盾：**LLM 的上下文窗口有限，但对话可能很长**。

### 存储层
- 每条消息存入 SQLite 的 Message 表
- 每个对话（Conversation）可以有多条消息
- 消息记录角色（user/assistant）和内容

### 上下文管理策略
- 每次调用 LLM 时，不会把所有历史都塞进去
- 只取**最近 N 轮**对话作为历史上下文
- 对话还有 `summary` 字段，可以存储较早对话的摘要

### 为什么需要对话历史
用户经常会问后续问题：
```
用户：什么是 Transformer？
助手：Transformer 是一种基于自注意力机制的模型...
用户：它和 RNN 有什么区别？   ← 这里的「它」需要对话历史才能理解
```

没有历史上下文，LLM 无法理解「它」指的是 Transformer。

## Q4：RAG Chain 的执行流程是什么？

**A：** 从用户输入到最终回答，RAG Chain 的完整流程：

```
1. 接收用户问题

2. 检索阶段
   └─ 调用 HybridRetriever → RRF → Reranker → 父块内容

3. 上下文组装
   ├─ 将检索到的父块格式化为带来源标注的参考资料
   ├─ 加载最近 N 轮对话历史
   └─ 组装完整 Prompt

4. LLM 调用
   ├─ 通过 ModelRouter 获取用户配置的模型
   ├─ 发送 Prompt
   └─ 接收 LLM 回答（支持流式输出）

5. 后处理
   ├─ 提取回答中的引用标注
   ├─ 将用户问题和助手回答存入数据库
   └─ 返回回答 + 引用信息给前端
```

## Q5：什么是流式输出（Streaming）？为什么要支持？

**A：**

### 问题背景
LLM 生成一个完整回答可能需要 5-15 秒。如果等全部生成完再显示，用户体验很差——看着空白屏幕等十几秒。

### 流式输出
LLM API 支持**边生成边返回**——每生成几个字就发送一次，前端实时追加显示。

用户体验上表现为：回答像「打字机」一样一个字一个字出现，感觉更自然、更快速。

### 实现方式
- LLM 调用时指定 `streaming=True`
- 返回的是一个迭代器/生成器
- 前端用 Streamlit 的 `st.write_stream()` 实时渲染

## Q6：引用（Citations）是如何工作的？

**A：** 引用系统让用户可以验证回答的可靠性。

### 实现思路
1. **组装 Prompt 时**：每个文本块前标注来源（文档名、页码）
2. **要求 LLM**：在回答中用标记引用来源
3. **后处理**：从 LLM 回答中提取引用标记
4. **前端展示**：引用以可折叠的形式展示，点击可查看原文

### 引用的价值
- **可信度**：用户知道每句话来自哪份资料的哪一页
- **可追溯**：如果回答有疑问，用户可以回到原文核实
- **学习辅助**：用户可以沿着引用深入阅读原始材料

这是 RAG 相比普通 LLM 对话的核心优势之一。

## Q7：用户在问答页面可以调整哪些偏好？

**A：** 系统支持多种用户偏好设置：

| 偏好 | 选项 | 影响 |
|------|------|------|
| **回答风格** | 详细 / 简洁 / 学术 | 影响 Prompt 中对回答风格的要求 |
| **回答篇幅** | 短 / 中 / 长 | 控制 LLM 输出的长度 |
| **引用显示** | 显示 / 隐藏 | 前端是否展示引用来源 |
| **澄清问题** | 开启 / 关闭 | 问题不清楚时 LLM 是否先反问 |
| **文档范围** | 全部 / 指定文档 | 限制检索范围 |

这些偏好通过修改 Prompt 或调整检索参数来实现。

## Q8：普通问答和苏格拉底对话有什么区别？

**A：** 这是两种完全不同的教学理念：

| 维度 | 普通问答 | 苏格拉底对话 |
|------|---------|-------------|
| **目标** | 给出答案 | 引导用户自己思考出答案 |
| **LLM 角色** | 知识讲解者 | 提问引导者 |
| **Prompt 策略** | 「基于资料回答问题」 | 「不要直接给答案，用问题引导」 |
| **对话结构** | 一问一答 | 多轮引导，逐步深入 |
| **适用场景** | 查资料、快速获取信息 | 深入理解概念、培养思考能力 |

用户可以在问答页面切换这两种模式。

---

## Q9：如果用户的问题和资料完全不相关，系统会怎样？

**A：** 设计上有几道防护：

1. **检索层**：返回的文本块相关度都很低
2. **Prompt 指令**：明确要求 LLM「如果提供的参考资料无法回答这个问题，请诚实告知用户」
3. **LLM 回答**：会说类似「根据您上传的资料，我没有找到与此相关的内容。建议您上传相关资料后再次提问。」

这比普通 LLM 好——普通 LLM 可能会编造答案，而 RAG 系统会坦诚告知自己无法回答。

---

## Q10：Prompt 工程在这个项目中有多重要？

**A：** 非常重要。Prompt 设计直接决定了：

| Prompt 设计 | 影响 |
|------------|------|
| 是否要求引用来源 | 决定回答是否可追溯 |
| 是否限制知识来源 | 决定是否产生幻觉 |
| 对话历史的组织方式 | 决定多轮对话的连贯性 |
| 回答格式要求 | 决定输出的可读性 |
| 苏格拉底式指令 | 决定是「教」还是「引导」 |

本项目将 Prompt 模板集中管理在 `prompts.py` 中，便于统一维护和迭代优化。

---

## Q11：RAG 系统有哪些常见的失败模式？

**A：** 了解失败模式有助于理解设计决策的动机：

| 失败模式 | 原因 | 本项目的应对 |
|---------|------|------------|
| **检索失败** | 问题和文档表述差异大 | 混合检索（语义+关键词）互补 |
| **上下文不足** | 块太小，信息不完整 | 父文档检索，返回大块 |
| **上下文噪声** | 不相关块混入 | 重排序过滤 |
| **幻觉** | LLM 忽略上下文自行发挥 | Prompt 严格限制 + 引用标注 |
| **多轮脱节** | 忘记之前的对话 | 对话历史管理 |
| **回答冗长** | LLM 过度展开 | 用户可调篇幅偏好 |
