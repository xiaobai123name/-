# 10 认证系统

> 理解用户注册、登录、登录态持久化的设计逻辑。

---

## Q1：为什么一个学习工具需要用户认证？

**A：** 认证不是为了「安全」（这不是银行系统），而是为了**数据隔离和个性化**：

| 需求 | 为什么需要认证 |
|------|-------------|
| 数据隔离 | 不同用户的文档、对话、答题记录互不可见 |
| 个性化 | 知识追踪、模型偏好都是基于用户的 |
| 状态持续 | 用户关闭浏览器后重新打开，希望保持登录 |
| 进度保存 | 学习进度需要关联到特定用户 |

## Q2：认证系统的整体架构是什么？

**A：** 分为三层：

```
┌─────────────────────────────────────────┐
│  前端认证层（app/auth_cookie.py）         │
│  Cookie 管理 + URL Token                │
└──────────────────┬──────────────────────┘
                   │
┌──────────────────▼──────────────────────┐
│  后端认证服务（backend/auth/auth_service）│

                   │

│  数据库层（User 表）                      │

└─────────────────────────────────────────┘
```

## Q3：密码是如何存储的？为什么不能明文存储？

**A：**

### 为什么不能明文
如果数据库泄露（被入侵、误上传到 Git 等），明文密码会直接暴露所有用户的密码。而且很多人在多个网站用相同密码，一处泄露处处受害。

### 本项目的做法
使用 **bcrypt** 哈希算法：
```
用户输入密码: "mypassword123"
    ↓ bcrypt 哈希
存入数据库: "$2b$12$LJ3m4vK9X..."（不可逆的哈希值）
```

### bcrypt 的特点
| 特性 | 说明 |
|------|------|
| **不可逆** | 无法从哈希值反推出原始密码 |
| **自带盐值** | 每次哈希结果不同，相同密码不会产生相同哈希 |
| **计算密集** | 故意设计得很慢，防止暴力破解 |

### 验证过程
```
用户输入密码: "mypassword123"
    ↓
bcrypt.checkpw(输入密码, 数据库中的哈希值)
    ↓
返回 True（匹配）或 False（不匹配）
```

## Q4：Streamlit 的登录态持久化面临什么挑战？

**A：** Streamlit 的两个特性导致登录态管理比传统 Web 框架困难：

### 挑战 1：脚本重执行
Streamlit 每次用户交互都重新执行脚本。虽然 `session_state` 可以在同一会话内保持状态，但**刷新页面或打开新标签页时 session_state 会丢失**。

### 挑战 2：缺乏原生会话管理
传统 Web 框架（Flask/Django）有成熟的 Session + Cookie 机制，Streamlit 没有内置这些。

### 用户期望
- 登录一次后，刷新页面不需要重新登录
- 关闭浏览器再打开，一段时间内不需要重新登录

## Q5：系统用什么方案解决登录态持久化？

**A：** 采用 **Cookie + URL Token 双通道**方案：

### 通道 1：Cookie
使用第三方库 `extra_streamlit_components` 的 CookieManager：
- 登录成功 → 写入 Cookie（键 `app_user_id`，值为用户 ID）
- 页面加载 → 读取 Cookie，恢复登录态
- 有效期 7 天

### 通道 2：URL Token
在浏览器 URL 中附加签名的 Token：
```
http://localhost:8501/?auth_token=1.1709827200.a3f5b7...
```
- `1`：用户 ID
- `1709827200`：时间戳
- `a3f5b7...`：HMAC-SHA256 签名

### 为什么要双通道？
| 情况 | Cookie | URL Token |
|------|--------|-----------|
| 正常刷新 | 有效 | 有效 |
| Cookie 被浏览器禁用 | 失败 | 有效 |
| 分享链接给自己 | 无效（Cookie 是设备绑定的） | 无效（Token 已过期） |
| 第三方库加载延迟 | 可能失败 | 有效 |

两种方案互为备份，提高登录态恢复的成功率。

## Q6：URL Token 的签名机制是怎么工作的？

**A：**

### 签名目的
防止伪造。如果 Token 只是 `user_id.timestamp`，任何人都能构造一个假 Token 冒充其他用户。

### 签名过程
```
签名密钥（存在 data/.auth_signing_key，首次启动自动生成）
    +
待签名数据: "user_id.timestamp"
    ↓ HMAC-SHA256
签名值: "a3f5b7c9d2..."
    ↓
最终 Token: "user_id.timestamp.signature"
```

### 验证过程
```
收到 Token: "1.1709827200.a3f5b7c9d2..."
    ↓
用相同密钥对 "1.1709827200" 重新计算签名
    ↓
比较计算结果和 Token 中的签名
    ├─ 一致 → Token 有效
    └─ 不一致 → Token 被篡改，拒绝
```

### 时效性
Token 包含时间戳，验证时检查是否过期（超过有效期则拒绝）。

## Q7：登录恢复的完整流程是什么？

**A：**

```
页面加载
    │
    ├─ 检查 session_state 中是否已有用户 → 有，直接返回（ready）
    │
    ├─ 尝试从 Cookie 恢复
    │   ├─ Cookie 中有 user_id → 从数据库查询用户
    │   │   ├─ 用户存在 → 恢复成功（restored）
    │   │   └─ 用户不存在 → Cookie 无效，继续
    │   └─ Cookie 中没有 user_id → 继续
    │
    ├─ 尝试从 URL Token 恢复
    │   ├─ URL 中有 auth_token → 验证签名和时效
    │   │   ├─ 有效 → 恢复成功（restored）
    │   │   └─ 无效 → Token 过期或被篡改
    │   └─ URL 中没有 auth_token → 继续
    │
    └─ 都没有 → 返回（missing），显示登录页
```

### 特殊状态：pending
Cookie 管理器需要时间初始化（异步加载），在初始化完成之前会返回 `pending` 状态。此时页面显示「正在恢复登录状态...」，等待 Cookie 管理器就绪后重新检查。

## Q8：注册时做了哪些验证？

**A：**

| 验证项 | 规则 | 原因 |
|--------|------|------|
| 用户名非空 | 不能为空字符串 | 基本要求 |
| 用户名唯一 | 数据库中不能重复 | 防冲突 |
| 密码长度 | 至少 N 位 | 基本安全性 |
| 密码确认 | 两次输入一致 | 防止手误 |

注册成功后自动登录（写入 Cookie + URL Token），无需再手动登录。

---

## Q9：退出登录时做了什么？

**A：**

```
用户点击退出
    │
    ├─ 清除 session_state 中的用户信息
    │
    ├─ 清除 Cookie（删除 app_user_id）
    │
    ├─ 清除 URL 中的 auth_token 参数
    │
    └─ 跳转回主页（显示登录界面）
```

三个通道全部清除，确保退出是彻底的。

## Q10：这个认证方案有什么局限性？

**A：** 作为学习工具的认证方案，有意做了简化：

| 局限 | 说明 | 在什么场景会成问题 |
|------|------|------------------|
| **无 HTTPS** | 本地运行时 Cookie 和 Token 明文传输 | 部署到公网时不安全 |
| **无会话过期** | Cookie 7 天有效，无主动过期机制 | 公用电脑上其他人可能访问 |
| **无多设备管理** | 无法查看/踢出其他设备的登录 | 多设备场景 |
| **单因素认证** | 只有密码，没有验证码/二次验证 | 高安全需求场景 |

这些简化对于**本地运行的个人学习工具**来说是合理的。如果要部署为公开服务，需要加强安全措施。

## Q11：签名密钥是如何管理的？

**A：**

- 存储位置：`data/.auth_signing_key` 文件
- 生成时机：首次启动时自动生成随机密钥
- 生命周期：整个应用运行期间不变
- 安全性：在 `.gitignore` 中排除，不会提交到版本控制

如果密钥文件丢失，所有已发出的 URL Token 都会失效（签名无法验证），用户需要重新登录。但 Cookie 通道不受影响（Cookie 存的是明文 user_id）。
