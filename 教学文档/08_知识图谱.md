# 08 知识图谱

> 理解如何从文档中自动抽取知识结构，并进行可视化展示。

---

## Q1：什么是知识图谱？它在学习场景中有什么价值？

**A：**

### 知识图谱是什么
知识图谱是一种**用图结构表示知识的方式**：
- **节点（Entity）**：表示概念、公式、人物等
- **边（Relation）**：表示概念之间的关系

```
[Transformer] ──包含──→ [自注意力机制]
[自注意力机制] ──前置知识──→ [矩阵乘法]
[BERT] ──基于──→ [Transformer]
```

### 学习场景中的价值
1. **全局视图**：一张图看清整门课程的知识结构
2. **关联发现**：发现自己没注意到的概念关联
3. **学习规划**：从图中看出哪些是前置知识，应该先学什么
4. **薄弱定位**：结合知识追踪，在图上标出薄弱区域

---

## Q2：知识图谱是怎么构建的？整体流程是什么？

**A：** 构建流程可以分为四大步骤：

```
1. 准备阶段
   └─ 从数据库加载文档的父块

2. 块合并
   └─ 将语义相似的小块合并成更大的语义单元

3. LLM 抽取
   └─ 让 LLM 从每个文本块中抽取实体和关系

4. 实体对齐
   └─ 合并指代同一概念的不同实体（如"注意力"和"Attention"）
```

最终产出一个包含实体列表和关系列表的知识图谱数据结构。

---

## Q3：为什么要在 LLM 抽取之前做块合并？

**A：** 两个原因：

### 1. 减少 LLM 调用次数
如果有 100 个小块，需要调用 100 次 LLM。合并成 30 个大块后只需要 30 次。
- 节省 API 费用
- 减少总耗时（受速率限制的影响更小）

### 2. 提供更完整的上下文
单独一个小块可能只包含一个概念的部分描述，LLM 难以正确抽取。合并后的块包含更完整的论述，抽取质量更高。

### 合并策略
- **语义合并**：计算块之间的嵌入相似度，相似度 ≥ 0.75 的块合并
- **大小合并**：合并后的块不超过配置的最大字符数

---

## Q4：LLM 是如何从文本中抽取实体和关系的？

**A：** 通过精心设计的 Prompt，要求 LLM 以结构化 JSON 格式输出。

### 实体抽取
要求 LLM 识别文本中的：

| 实体类型 | 说明 | 举例 |
|---------|------|------|
| concept | 核心概念 | 注意力机制、反向传播 |
| formula | 数学公式 | softmax 函数、交叉熵损失 |
| theorem | 定理/原理 | 万能近似定理 |
| example | 实例/案例 | ImageNet 竞赛 |
| person | 人物 | Vaswani、Hinton |
| method | 方法/算法 | 梯度下降、Adam 优化器 |
| application | 应用领域 | 机器翻译、图像分类 |

### 关系抽取
要求 LLM 识别实体之间的关系：

| 关系类型 | 含义 | 举例 |
|---------|------|------|
| prerequisite | 前置知识 | 矩阵乘法 → 注意力机制 |
| leads_to | 导向/发展为 | RNN → LSTM |
| belongs_to | 属于 | 自注意力 → Transformer |
| example_of | 是...的例子 | BERT → 预训练模型 |
| similar_to | 相似 | GRU ↔ LSTM |
| contains | 包含 | Transformer → 编码器 |
| applies_to | 应用于 | CNN → 图像识别 |
| derived_from | 派生自 | GPT → Transformer |

### 输出格式
LLM 返回 JSON，每个实体有 name、type、description，每个关系有 source、target、type。

## Q5：什么是实体对齐？为什么需要它？

**A：**

### 问题
不同文本块中可能用不同的方式指代同一个概念：
- 「注意力机制」和「Attention Mechanism」
- 「自注意力」和「Self-Attention」
- 「Transformer 模型」和「Transformer」

如果不做对齐，图谱中会出现重复节点，关系也会断裂。

### 对齐策略（两阶段）

**阶段 1：嵌入相似度判断**
```
计算两个实体名称的嵌入向量相似度：
  - 相似度 ≥ 0.80 → 直接合并（高置信度）
  - 0.70 ≤ 相似度 < 0.80 → 进入阶段 2（不确定）
  - 相似度 < 0.70 → 不合并（明显不同）
```

**阶段 2：LLM 辅助判断**
```
将两个实体的名称和描述交给 LLM 判断：
  "注意力机制"（描述：一种让模型关注重要部分的机制）
  "Attention"（描述：A mechanism for focusing on relevant parts）
  → LLM 判断：是同一概念 → 合并
```

### 为什么用两阶段而不是全用 LLM？
- 如果 100 个实体两两比较，需要 C(100,2) = 4950 次 LLM 调用
- 先用嵌入相似度快速筛选，只有「模棱两可」的才请 LLM 判断
- 大大减少 LLM 调用次数

## Q6：多文档知识图谱有什么不同的构建策略？

**A：** 当用户选择多篇文档一起构建图谱时，有两种策略：

### 策略 1：逐文档构建再合并（per_doc）
```
文档 A → 子图谱 A
文档 B → 子图谱 B
文档 C → 子图谱 C
    ↓
合并三个子图谱 → 全局实体对齐 → 最终图谱
```
- 优点：每份文档独立处理，可以复用之前的缓存
- 缺点：跨文档的关系可能遗漏

### 策略 2：全局构建（global）
```
文档 A + B + C 的所有块混合在一起
    ↓
统一进行块合并 → 统一 LLM 抽取 → 实体对齐 → 最终图谱
```
- 优点：能发现跨文档的关系
- 缺点：无法复用缓存，每次都要重新构建

用户可以在前端选择策略。

## Q7：知识图谱构建为什么需要速率限制和并发控制？

**A：** 因为知识图谱构建是整个系统中 **LLM 调用最密集的操作**。

### 调用量估算
假设一份文档有 50 个文本块：
- 块合并的嵌入计算：50 次嵌入调用
- LLM 抽取：合并后约 20 次 LLM 调用
- 实体对齐的嵌入计算：可能几十次
- 实体对齐的 LLM 判断：可能几次到几十次

总计可能需要 100+ 次 API 调用。

### 如果不做限制会怎样？
- API 供应商会返回 429（Too Many Requests）错误
- 账户可能被临时封禁
- 大量请求堆积导致内存/网络问题

### 控制机制
| 机制 | 作用 |
|------|------|
| **信号量（Semaphore）** | 限制同时进行的 LLM 调用数量 |
| **最小请求间隔** | 两次调用之间至少间隔 N 秒 |
| **RPM 限制** | 每分钟最多调用 N 次 |
| **异步执行** | 多个调用异步并发（在限制范围内） |

## Q8：知识图谱的缓存机制是怎么设计的？

**A：** 因为构建成本高，所以缓存非常重要。

### 两级缓存
1. **内存缓存**：构建完的图谱保存在内存中，同一会话内直接复用
2. **数据库缓存**：存入 SQLite 的 KnowledgeGraphCache 表，跨会话复用

### 缓存失效判断
```
构建请求
    │
    ├─ 计算当前文档内容的哈希值（source_hash）
    │
    ├─ 与缓存中的 source_hash 比较
    │     ├─ 相同 → 返回缓存的图谱
    │     └─ 不同 → 文档内容变了，重新构建
    │
    └─ 缓存不存在 → 首次构建
```

**哈希值的计算依据**：所有源文本块内容的拼接哈希。只要文档内容不变，哈希值不变，缓存就有效。

## Q9：知识图谱的前端可视化是如何实现的？

**A：** 使用 `streamlit-agraph` 库进行交互式图可视化。

### 可视化元素
- **节点**：不同类型的实体用不同颜色和大小
  - 概念类（concept）：较大节点
  - 公式类（formula）：特殊颜色
  - 人物类（person）：另一种颜色
- **边**：不同关系类型用不同颜色/样式的连线
- **交互**：点击节点查看详情，拖拽调整布局

### 显示设置
用户可以调整：
| 设置 | 作用 |
|------|------|
| 布局算法 | 图的自动排列方式 |
| 聚焦模式 | 只显示选中节点的邻居 |
| 邻域深度 | 聚焦时展示几层关联 |
| 公式简化 | 是否简化显示公式内容 |
| 画布尺寸 | 可视化区域大小 |

### 节点详情
点击节点会显示：
- 实体类型和描述
- 来源文档
- 所有关联的实体和关系
- 如果是公式，展示公式内容

## Q10：知识图谱的实体类型和关系类型是如何确定的？

**A：** 这些类型是**预定义的枚举值**，在 Prompt 中告诉 LLM。

### 设计考量
- 类型太少 → 图谱表达力不够
- 类型太多 → LLM 分类不准确
- 当前的类型集合是在学术文档场景下平衡后的选择

### 实体类型覆盖
```
concept（概念）── 最常见，如"注意力机制"
formula（公式）── 数学表达式
theorem（定理）── 已证明的结论
example（实例）── 具体案例
person（人物）── 重要学者
method（方法）── 具体算法或方法
application（应用）── 实际应用场景
```

### 关系类型覆盖
```
prerequisite（前置知识）── 学习顺序
leads_to（发展为）── 技术演进
belongs_to（属于）── 分类关系
contains（包含）── 组成关系
example_of（是例子）── 示例关系
similar_to（相似）── 类比关系
applies_to（应用于）── 应用关系
derived_from（派生自）── 衍生关系
```

## Q11：知识图谱构建中有哪些容错设计？

**A：**

| 潜在问题 | 应对措施 |
|---------|---------|
| LLM 返回的 JSON 格式不合法 | 多次重试，对硅基流动等用更严格的 Prompt |
| LLM 漏掉某些实体 | 多块覆盖，同一实体可能在不同块中被提取 |
| 实体对齐错误（不该合并的合并了） | 高阈值（0.80），宁可不合并也不错合并 |
| API 调用失败 | 重试机制 + 跳过失败的块继续处理 |
| 构建耗时太长 | 缓存机制避免重复构建 |
