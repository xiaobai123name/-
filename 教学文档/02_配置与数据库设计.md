# 02 配置管理与数据库设计

> 理解系统的「骨架」——配置如何管理、数据如何组织。

---

## Q1：系统的配置项分为哪几类？为什么需要配置管理？

**A：** 配置项分为五大类：

| 类别 | 举例 | 为什么需要配置化 |
|------|------|----------------|
| **API 密钥** | Google API Key、硅基流动 Key | 密钥不能硬编码在代码里，需要从环境变量读取 |
| **存储路径** | 数据库路径、上传目录 | 不同环境（开发/部署）路径可能不同 |
| **模型参数** | 默认 LLM 模型名、嵌入模型名 | 模型可能更新换代，需要灵活切换 |
| **RAG 参数** | 分块大小、检索数量、重排数量 | 不同场景下最优参数不同，需要可调 |
| **KG 参数** | 并发数、速率限制、合并阈值 | 知识图谱构建涉及大量 API 调用，需要精细控制 |

**设计决策**：使用 Pydantic Settings，从 `.env` 文件读取配置，所有配置项都有默认值。好处是类型安全、有验证、IDE 有补全。

---

## Q2：`.env` 和 `.env.example` 的关系是什么？为什么要这样设计？

**A：**

- `.env.example` 是**模板**，提交到 Git 仓库，包含所有配置项的说明和默认值（敏感值留空）
- `.env` 是**实际配置**，不提交到 Git（在 `.gitignore` 中），包含真正的 API 密钥

这种模式的好处：
1. 新开发者克隆仓库后，复制 `.env.example` 为 `.env`，填入自己的密钥即可
2. 密钥不会意外泄露到版本控制
3. `.env.example` 充当了配置文档的角色

## Q3：为什么选择 SQLite 而不是 MySQL/PostgreSQL？

**A：** 这是一个**场景驱动的选型**：

| 考量因素 | SQLite 的优势 |
|---------|--------------|
| **部署复杂度** | 零配置，无需安装数据库服务 |
| **用户规模** | 本项目是单用户/少量用户的学习工具，不需要高并发 |
| **数据量** | 学习资料通常不会超过 GB 级别 |
| **可移植性** | 单个文件，备份/迁移只需复制一个 `.db` 文件 |
| **开发效率** | 不需要数据库运维知识 |

**如果未来要支持多用户并发访问，SQLite 会成为瓶颈**，那时再考虑换成 PostgreSQL。

## Q4：数据库中有哪些表？它们之间的关系是什么？

**A：** 共 8 张表，可以分成 4 个领域：

### 用户领域
```
User（用户）
  │
  ├── UserModelPreference（用户模型偏好）
  │     用户可以为不同模块配置不同的 LLM
  │
  └── 一对多关系 → Document, Conversation, KnowledgeState, QuizAttempt
```

### 文档领域
```
Document（文档）
  │
  └── Chunk（文本块）
        每个文档被切成多个块
        块分两级：parent（父块，大）和 child（子块，小）
        子块通过 parent_chunk_id 关联到父块
```

### 对话领域
```
Conversation（对话）
  │
  └── Message（消息）
        每轮对话包含多条消息（用户/助手交替）
        对话有模式：normal / socratic / quiz
```

### 学习领域
```
KnowledgeState（知识状态）
  记录每个知识点的掌握率

QuizAttempt（答题记录）
  记录每次答题的详细信息

KnowledgeGraphCache（知识图谱缓存）
  缓存已构建的知识图谱，避免重复调用 LLM
```

## Q5：为什么 Chunk 表要区分 parent 和 child？

**A：** 这是 RAG 系统中非常重要的设计——**父子块分离策略**。

**问题背景**：
- 如果文本块太小（比如 200 字），检索精准但 LLM 看到的上下文太少，回答不完整
- 如果文本块太大（比如 5000 字），上下文完整但检索不精准，容易引入噪声

**解决方案**：
- **子块（child，~500 字）**：用于检索，小而精准
- **父块（parent，~2000 字）**：用于生成，大而完整
- 检索时匹配子块 → 找到对应的父块 → 把父块内容送给 LLM

数据库中通过 `parent_chunk_id` 字段建立子块到父块的关联。

## Q6：KnowledgeState 表是怎么实现知识追踪的？

**A：** 设计思路是**基于答题统计的简单知识追踪**：

| 字段 | 含义 |
|------|------|
| `knowledge_point` | 知识点名称（由 LLM 从题目中提取） |
| `attempts` | 该知识点被考过几次 |
| `correct_count` | 答对几次 |
| `mastery_rate` | 掌握率 = correct_count / attempts |
| `is_weak_point` | 是否为薄弱点（掌握率 < 60% 且答题 ≥ 3 次） |

**设计决策**：
- 至少答 3 次才判定薄弱，避免偶然失误导致误判
- 60% 作为薄弱阈值，低于此需要重点复习
- 出题时对薄弱知识点进行加权采样，答得越差出题越多

## Q7：UserModelPreference 表解决了什么问题？

**A：** 解决的是**不同功能模块需要不同模型**的问题。

比如：
- 问答模块需要高质量的回答 → 用 gemini-2.5-flash
- 知识图谱需要大量调用但对质量要求稍低 → 用便宜的模型
- 测验生成 → 可以用另一个模型

每个用户可以独立配置每个模块使用的：
- 供应商（Google / 硅基流动 / Antigravity）
- 模型名称
- 温度（temperature）
- API 地址

这样实现了**模块级别的模型灵活配置**。

## Q8：KnowledgeGraphCache 的设计意图是什么？

**A：** 知识图谱构建是**最昂贵的操作**——需要对每个文本块调用 LLM 提取实体和关系，一份文档可能需要几十次 LLM 调用。

缓存策略：
1. 构建完成后，将图谱数据序列化为 JSON 存入数据库
2. 用 `source_hash`（源文档内容的哈希值）作为缓存键
3. 下次请求同一组文档时，先检查 `source_hash` 是否变化
4. 如果文档没变，直接返回缓存；如果变了，重新构建

这样避免了用户每次查看知识图谱都要等待漫长的构建过程。

## Q9：QuizAttempt 表为什么要存 followup_question？

**A：** 这是**错题追问**功能的数据支撑。

当用户答错一道题时，系统会：
1. 给出正确答案和解析（`explanation`）
2. 生成一道针对性的追问题（`followup_question`）

追问题的目的是确认用户是否真正理解了错误原因，而不只是看了答案就过去。这个字段存在答题记录中，方便用户后续在错题本中重新练习。

## Q10：Conversation 表的 mode 字段区分了什么？

**A：** 系统中有三种对话模式：

| 模式 | 含义 | 交互特点 |
|------|------|---------|
| `normal` | 普通 RAG 问答 | 用户问，系统答，带引用 |
| `socratic` | 苏格拉底对话 | 系统用引导性问题启发用户 |
| `quiz` | 测验对话 | 测验过程中的问答记录 |

分开存储的好处是：
- 不同模式的对话可以分别管理和回顾
- 统计分析时可以按模式筛选（比如只看苏格拉底对话的学习效果）
- 主页仪表盘可以分类展示最近活动

---

## Q11：Message 表的 citations 字段存储什么？

**A：** 存储的是 **RAG 回答的引用来源**，JSON 格式，通常包含：
- 源文档名称
- 相关文本块内容
- 页码信息

这样用户可以验证回答的可靠性——点击引用即可看到原始资料中的相关段落。这是 RAG 系统区别于普通 LLM 对话的核心特性之一。

## Q12：为什么向量数据存在 ChromaDB 而不是 SQLite？

**A：** 这涉及两种数据库的本质区别：

| 能力 | SQLite | ChromaDB |
|------|--------|----------|
| 存储结构化数据 | 擅长 | 不适合 |
| 存储向量并做相似度搜索 | 不支持 | 专门为此设计 |
| 近似最近邻搜索（ANN） | 无 | 内置 HNSW 索引 |

向量搜索需要专门的索引结构（如 HNSW）来实现高效的近似最近邻搜索，这不是关系数据库擅长的事情。

因此项目采用**双数据库架构**：
- **SQLite**：存储用户、文档、对话、知识状态等结构化数据
- **ChromaDB**：存储文本块的向量表示，支持语义相似度搜索

两者通过 `document_id` 和 `chunk_id` 关联。
